# Инструкции репозитория кабинета заказчика МОСТ

## Область действия

- Эти правила действуют во всём репозитории. Более вложенный `AGENTS.md` может уточнять их для своей директории.
- Продукт называется **МОСТ**. `prohelper_customers` — только техническое имя репозитория.
- Всегда общайся на русском языке. Пользовательские тексты должны быть понятны заказчику и не раскрывать внутренние технические термины.

## Коммиты и Pull Request

- Заголовки коммитов и PR пиши по-русски в формате `type[scope]: описание`. Типы: `fix`, `feat`, `refactor`, `test`, `docs`, `chore`. В `scope` указывай функциональную область (`договоры`, `акты`, `отчёты`); общее название интерфейса используй только для изменений без одной функциональной области.
- Описание PR заполняй по русскому шаблону `.github/pull_request_template.md`: зачем изменение, что сделано, что фактически проверено, риски и действия при выпуске. Для бага добавляй причину; `Closes #...` — только при существующей задаче. Не оставляй пустые подсказки.
- При разрешённом слиянии используй `Squash and merge` и проверь итоговое сообщение коммита.

## Git, безопасность и окружение

- Не работай напрямую в `main`: обновляй его только fast-forward, создавай отдельную ветку и передавай изменения через Pull Request.
- Не коммить, не push, не создавай PR, не merge и не deploy без отдельной явной команды. Не изменяй и не откатывай чужие файлы.
- Перед правками проверяй ветку и `git status`. Не используй `git reset --hard`, принудительный checkout, широкое рекурсивное удаление или очистку неотслеживаемых файлов без прямого разрешения.
- Не изменяй CI/CD, GitHub Actions и deployment-конфигурацию без отдельного запроса.
- Не добавляй `.env`, ключи, токены, пароли, production-данные, локальные пути пользователя, логи, кеши, `node_modules`, сборочные артефакты и зависимости.
- Не создавай SSH-ключи и не предполагай production-доступ. Production-диагностика возможна только после отдельной явной выдачи владельцем read-only доступа для конкретной задачи; операции записи и раскрытие секретов запрещены.
- Не запускай dev-сервер или сборку без прямой необходимости и согласования. Для документальных правок не запускай сборки и тесты.

## Архитектура React/Vite

- Используй версии React, TypeScript и Vite из `package.json`; major-обновления выполняй только отдельной задачей.
- Используй функциональные компоненты и hooks. Отделяй UI от feature-контейнеров, API-клиентов, состояния и route guards; переиспользуй существующие проектные паттерны.
- Backend остаётся источником бизнес-правил, permissions, ownership и валидации. Не переноси доменную защиту на клиент и не исправляй серверные расхождения скрытыми workaround-ами.
- Особо защищай границы заказчика, организации, проекта и документов: клиент должен передавать правильный контекст, но сервер обязан повторно проверять доступ.
- Для каждого сценария предусматривай loading, error, empty и success-состояния, предотвращение повторной отправки, адаптивность и клавиатурную доступность.

## API, права и переводы

- Используй типизированные API-клиенты и контракт `CustomerResponse`. Явно согласуй request/response shape, nullable-поля, ошибки, pagination/meta и обратную совместимость.
- Для контрактных объектов, mapper-функций и discriminated unions используй явные типы, `as const` и `satisfies`, где это укрепляет форму данных.
- Используй permissions backend и существующие route/component guards. Скрытие кнопки или маршрута не заменяет серверную проверку доступа.
- Используй существующий механизм локализации. Не показывай ключи переводов, permission slug-и, stack traces и внутренние сообщения; русский текст сохраняй в корректной UTF-8.
- Ошибки должны подсказывать заказчику безопасное следующее действие и не раскрывать существование недоступных сущностей или чувствительные данные.

## Проверки

- Для документации и текстов без изменения поведения не запускай сборку и тесты; проверь diff, Markdown, UTF-8 и отсутствие секретов.
- После изменений TypeScript, API-клиентов, типов, hooks или состояния запускай `npx tsc --noEmit` и ESLint только для затронутых файлов или минимального модуля.
- Для бизнес-логики, сетевых сценариев, документов, прав и сложного UI-состояния запускай целевые Vitest-тесты; для HTTP-моков предпочитай MSW. Воспроизводимый баг покрывай регрессионным тестом.
- В итоговом ответе перечисли изменённые файлы, выполненные проверки и причины пропуска остальных.
